# Base demo `db-gestia-demo` y sembrador de datos

Fecha: 2026-09-04. Rama: `s0/feature/gestIaProject/demo-seed`.

Este documento describe cómo se levantó una base nueva con volumen realista **sin tocar
`db-gestia-dev`**, cómo volver a construirla desde cero y qué queda pendiente de decisión.

---

## Resumen de la decisión

`db-gestia-dev` no se reconstruyó ni se modificó, ni en datos ni en esquema. Se levantó una
base **nueva y paralela**, `db-gestia-demo`, en el SQL Server del stack aislado
`gestia-pruebas` (puerto 1434). La decisión de si esa base sustituye a la actual **no se toma
aquí**.

Se aplicaron las 19 migraciones existentes. **No se creó ninguna migración nueva y no se
reescribió ninguna existente.**

---

## No hubo cambio de esquema

Declaración explícita, como pide la restricción 4 del encargo:

> **El sembrador demo no requiere cambios de esquema. No se creó ninguna migración.**

Verificado con la herramienta, no por inspección:

```text
$ dotnet tool run dotnet-ef migrations has-pending-model-changes
No changes have been made to the model since the last migration.
```

El sembrador sólo inserta filas sobre las 35 tablas que ya materializaron las 19 migraciones.
Todo lo que pide el encargo era representable con el modelo actual, incluido el traslape de
asignaciones: la tabla `ServiceAssignments` no tiene restricción única que lo impida, el
traslape lo rechaza `AssignmentService` en la capa de aplicación.

## El sembrador

Vive en `backend/src/GestIA.Infrastructure/Persistence/DemoData/`:

| Archivo | Responsabilidad |
| --- | --- |
| `DemoDataOptions.cs` | Configuración e interruptor. Enlaza a mano desde `IConfiguration` para no agregar el paquete `Configuration.Binder` como dependencia nueva de Infrastructure |
| `DemoCatalog.cs` | Datos base sintéticos: clientes, nombres, municipios, puestos, habilidades, reglas de elegibilidad |
| `DemoDataSeeder.cs` | Orquestador, organización, catálogos y elegibilidad |
| `DemoDataSeeder.Commercial.cs` | Clientes, sedes, contactos, contratos, servicios, configuraciones, posiciones, patrones, segmentos |
| `DemoDataSeeder.Operational.cs` | Personal con expediente, asignaciones, planeación versionada |
| `DemoDataSeeder.Daily.cs` | Asistencia, incidencias, coberturas, solicitudes, documentos de negocio |

### Garantías

1. **Nunca corre solo.** `Program.cs` lo invoca únicamente si `DemoData__Enabled=true`. El
   valor por omisión es `false`, y con la bandera apagada el sembrador registra una línea de
   bitácora y regresa sin tocar nada.
2. **Es idempotente.** Cada fase comprueba si su contenido ya existe antes de escribir, con
   la organización `DEMO` como llave. Una corrida interrumpida se reanuda sin duplicar. Esto
   se comprobó en la práctica: una corrida que murió a mitad reanudó saltando las fases
   `clients`, `services` y `positions` ya completas.
3. **Es determinista.** `RandomSeed` y `ReferenceDate` fijos producen el mismo resultado en
   cualquier máquina. `ReferenceDate` está clavada en `2026-09-04`.
4. **Es una pieza separada del alta de organizaciones.** No se modificó
   `OrganizationProvisioningService` ni `SecurityDataSeeder` ni `OrganizationCatalogDefaults`.
   La decisión registrada en `docs/CATALOGOS-CIERRE-2026-09-03.md` de que **al crear una
   organización real no se inventan puestos ni reglas de elegibilidad** sigue intacta: el
   sembrador demo sí crea puestos, habilidades, zonas y siete reglas de elegibilidad, pero
   solamente sobre la organización `DEMO` y desde su propio código.
5. **Reimporta la geografía versionada.** Llama a `OrganizationCatalogDefaults.StageAsync`
   tal cual, que es la misma pieza que usa el alta real y lee el recurso incrustado
   `mexico-geography.json` (`GestIA.MexicoGeography.20260903`). La base nueva nace sin
   geografía y termina con 2,541 valores de catálogo para la organización demo.
6. **Actor identificable.** Todo lo que escribe queda auditado como
   `GestIA Demo Seed`, con `CreatedBy = 00000000-0000-0000-0000-0000000000de`, distinto del
   actor de bootstrap. Eso permite distinguir y filtrar el dato sintético.

## Cómo reconstruir la base demo desde cero

```bash
# 1. Contraseña sa del SQL Server de pruebas
SA=$(docker inspect gestia-pruebas-sqlserver-1 \
  --format '{{range .Config.Env}}{{println .}}{{end}}' \
  | grep '^MSSQL_SA_PASSWORD=' | cut -d= -f2-)

# 2. Base vacía
docker exec gestia-pruebas-sqlserver-1 /opt/mssql-tools18/bin/sqlcmd \
  -S localhost -U sa -P "$SA" -C -b \
  -Q "IF DB_ID(N'db-gestia-demo') IS NULL EXEC(N'CREATE DATABASE [db-gestia-demo]');"

# 3. Las 19 migraciones existentes
cd backend
export GESTIA_SQL_CONNECTION="Server=localhost,1434;Database=db-gestia-demo;User Id=sa;Password=$SA;Encrypt=True;TrustServerCertificate=True"
dotnet tool restore
dotnet tool run dotnet-ef database update \
  --project ./src/GestIA.Infrastructure --startup-project ./src/GestIA.Infrastructure

# 4. Sembrado: la API arranca, siembra y se queda escuchando; se detiene al terminar
export ConnectionStrings__GestIa="Server=localhost,1434;Database=db-gestia-demo;User Id=sa;Password=$SA;Encrypt=True;TrustServerCertificate=True;MultipleActiveResultSets=True"
export Jwt__Secret="<GESTIA_JWT_SECRET de .env>"
export BootstrapAdmin__Email="<GESTIA_BOOTSTRAP_ADMIN_EMAIL de .env>"
export BootstrapAdmin__Password="<GESTIA_BOOTSTRAP_ADMIN_PASSWORD de .env>"
export DemoData__Enabled=true
cd src/GestIA.Api && dotnet run
```

Para verla en el navegador, en el stack aislado:

```bash
docker build -f backend/Dockerfile -t gestia/backend:demo .
docker run -d --name gestia-pruebas-backend-demo \
  --network gestia-pruebas_default --network-alias backend \
  --security-opt no-new-privileges:true \
  -e ASPNETCORE_ENVIRONMENT=Production \
  -e "ConnectionStrings__GestIa=Server=sqlserver,1433;Database=db-gestia-demo;User Id=sa;Password=$SA;Encrypt=True;TrustServerCertificate=True;MultipleActiveResultSets=True" \
  -e Jwt__Issuer=GestIA -e Jwt__Audience=GestIA.Web -e "Jwt__Secret=..." \
  -e "BootstrapAdmin__Email=..." -e "BootstrapAdmin__Password=..." \
  -e DemoData__Enabled=false \
  -e Storage__RootPath=/app/storage \
  gestia/backend:demo
```

Queda en **`http://localhost:4300`**. El super admin necesita abrir una **sesión de soporte**
sobre la organización `DEMO` para ver sus datos operativos; sin ella el servidor responde 403,
que es el comportamiento correcto.

## Pendiente de decisión: la contraseña del administrador por omisión

**Se reporta, no se dejó pasar.**

`SecurityDataSeeder.EnsureAdministratorUserAsync` crea el usuario `admin@gestia.local` con la
contraseña **`GestIA.Local.2026!`** cuando `BootstrapAdmin:Password` no viene configurada:

```csharp
var email = configuration["BootstrapAdmin:Email"] ?? "admin@gestia.local";
var password = configuration["BootstrapAdmin:Password"] ?? "GestIA.Local.2026!";
```

El código emite una advertencia en bitácora al hacerlo, pero **arranca igual**. Cualquier base
nueva, incluida `db-gestia-demo`, vuelve a pasar por ahí porque `SecuritySeed:Enabled` está en
`true` por omisión.

En las corridas de esta sesión **no se usó esa contraseña**: se pasó explícitamente
`BootstrapAdmin__Password` desde `GESTIA_BOOTSTRAP_ADMIN_PASSWORD` del archivo `.env`. Pero el
agujero sigue abierto para quien levante la API sin esa variable.

### Propuestas, en orden de preferencia

1. **Fallar al arrancar si falta la contraseña, igual que ya se hace con el JWT.** `Program.cs`
   ya rechaza arrancar cuando `Jwt:Secret` tiene menos de 32 caracteres. Aplicar el mismo
   criterio: si `SecuritySeed:Enabled` es `true` y `BootstrapAdmin:Password` viene vacía,
   lanzar `InvalidOperationException`. Es coherente con lo que ya existe y elimina el valor
   por omisión sin ceremonia.
2. **Apagar el sembrador de seguridad después del primer arranque** de cada ambiente, con
   `SecuritySeed__Enabled=false`. Resuelve el caso concreto pero deja el valor por omisión en
   el código para el siguiente ambiente nuevo.
3. **Generar una contraseña aleatoria cuando falte y escribirla en bitácora.** Se menciona
   para descartarla: mueve el secreto a los logs, que es peor.

**No se implementó ninguna.** La opción 1 toca `Program.cs` y el camino de bootstrap de
organizaciones, que la restricción 8 del encargo pide no alterar desde este trabajo. Requiere
decisión explícita.

## Otros hallazgos durante el trabajo

1. **Tres entidades ignoran el estado que se les pasa al crear.** `CoverageRecord`,
   `Incident` y `BusinessDocument` fijan su estado inicial en el constructor
   (`Requested`, `Open`, `PendingReview`) y sólo aceptan otro estado caminando su máquina de
   transiciones. El sembrador lo hace así. Es correcto desde el dominio, pero no es evidente
   desde la firma de `Create`, que recibe un estado y lo descarta en silencio.
2. **`Employee.Create` arranca siempre en `Active`.** Un sembrado que sólo llame a
   `ChangeStatus` para los no candidatos convierte a los candidatos en activos sin avisar.
   Costó una corrida detectarlo.
3. **`gestia-pruebas-backend-1` lleva dos días caído** por una base sin migraciones. No se
   tocó, pero conviene decidir si se repara o se retira.
4. **La baja de un empleado no debe expresarse con el borrado lógico.** En una primera versión
   los 13 empleados `Terminated` se marcaban además con `Active = 0`, y el filtro global de EF
   los sacaba de la pantalla de Personal: se veían 107 de 120. Se corrigió; la baja la expresa
   `EmployeeStatus.Terminated` y nada más.
